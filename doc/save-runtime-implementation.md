# Save Runtime Implementation

## Goal

Add a `save` control-plane action that persists the current in-memory `runtime` ruleset back into the permanent `rules.d` directory.

This document records the V1 implementation semantics, API shape, file layout, and limitations.

## Scope

V1 `save` solves one narrow problem:

- `agctl apply --runtime --file ...` can change the daemon runtime ruleset
- `agctl save` writes that current runtime ruleset back to disk
- a later `reload` or daemon restart reads the same ruleset from `rules.d`

V1 does not attempt to preserve the user's original multi-file layout or comments.

## Chosen Semantics

The current permanent model is a directory:

```text
/etc/agentguardian/rules.d/
```

The loader merges all YAML files in lexical order.

Because of that, `save` cannot safely append one more generated file without changing semantics. The old files would still be merged together with the generated file and could create duplicate rules or different conflict resolution.

So V1 `save` uses this rule:

- replace the current `rules.d` contents with one generated ruleset file

Generated filename:

```text
000-generated-ruleset.yaml
```

This keeps permanent state deterministic after `save`.

## User-Facing Behavior

Command:

```bash
agctl save
```

Daemon API:

```text
POST /v1/runtime/save
```

Behavior:

1. Read current runtime ruleset from daemon memory
2. Reject if runtime is not loaded
3. Reject if runtime currently has an error state
4. Normalize and validate the runtime ruleset again
5. Write it to `rules.d/000-generated-ruleset.yaml`
6. Replace previous permanent YAML files
7. Return both runtime and permanent state in the response

## Data Flow

### Runtime Side

`Service.SaveRuntime()` reads:

- `runtimeLoaded`
- `runtimeError`
- `runtimeRuleset`

It refuses to save when:

- no runtime ruleset has been loaded yet
- runtime is marked invalid

### Persistence Side

`rules.SaveDir()` is responsible for disk persistence.

It:

1. normalizes the ruleset
2. validates the ruleset
3. marshals the whole ruleset to YAML
4. writes a temporary directory in the same parent directory
5. writes `000-generated-ruleset.yaml` into that temp directory
6. renames the old `rules.d` to a backup name
7. renames the temp directory to `rules.d`
8. deletes the backup directory after success

This keeps the generated permanent state self-contained and reloadable by the existing loader.

## Why Replace The Directory

Three alternatives were considered.

### Alternative 1: append a generated YAML file

Rejected because:

- old files would still be loaded
- duplicate rule IDs become likely
- merge order would affect behavior
- permanent would no longer equal the saved runtime snapshot

### Alternative 2: export to a separate file outside `rules.d`

Rejected for V1 because:

- it does not change actual permanent state
- daemon restart would still use the old `rules.d`
- user expectation of `save` is persistence, not export only

### Alternative 3: rewrite `rules.d` into one generated file

Chosen because:

- semantics are clear
- reload behavior stays deterministic
- implementation fits the current loader model

## API Shape

Response type:

```json
{
  "message": "runtime ruleset saved to permanent",
  "runtime": { "...": "..." },
  "permanent": { "...": "..." }
}
```

On error:

- HTTP status `422`
- response still carries runtime/permanent snapshots plus an error string

## File Format

Saved output is a full ruleset object, not one rule per file.

Example:

```yaml
# Generated by agctl save. Manual edits may be overwritten.
version: 1
rules:
  - id: runtime-hide
    enabled: true
    priority: 0
    match:
      path: /tmp/runtime
      comm: cat
    action:
      type: hide
```

This format is intentionally simple and fully compatible with the existing loader.

## Validation Rules

Before write, the ruleset still goes through normal rules validation, including:

- absolute path requirements
- selector exclusivity
- rewrite length checks
- field size limits

This means `save` does not bypass validation.

## Atomicity Model

V1 uses a best-effort filesystem replacement flow:

1. create temp directory
2. write generated file
3. rename existing `rules.d` to backup
4. rename temp directory to `rules.d`
5. remove backup

This is not a perfect transactional filesystem design, but it is good enough for the current single-daemon local workflow.

If the second rename fails, the implementation attempts to restore the backup directory.

## Limitations

V1 `save` still has these limits:

- it does not preserve original file split
- it does not preserve comments from old permanent files
- it does not preserve original file names
- it overwrites permanent state with one generated file
- it does not provide versioned history or rollback

These are acceptable for the first working runtime-to-permanent persistence path.

## Recommended Future Improvements

Follow-up work could add:

- `agctl export --runtime --file ...`
- `save --output <dir>`
- revision history for saved permanent states
- automatic backup retention
- a richer persistent store model that can preserve rule-level files

## Summary

V1 `save` establishes a complete control-plane loop:

1. apply a runtime ruleset
2. inspect runtime state
3. save runtime back to permanent
4. reload or restart from that saved permanent state

That closes the gap between temporary runtime changes and durable daemon configuration.
